# 版を上げる

`vMAJOR.MINOR.PATCH` の形のタグを push すると、GitHub Actions が配布物を組んで公開する。
main への push では検証しか走らず、配布物は出ない。

版数の決め方は 2 つに分かれている。

- **`versionName`** … タグ名から先頭の `v` を除いたもの。**人が決める**
- **`versionCode`** … コミット数（`git rev-list --count HEAD`）。**自動**。単調増加すればよく、
  版数との対応は気にしない

## 打つ前に確かめる

1. **main が push 済みで、CI が緑であること。**
   タグだけ先に push してもコミット自体は飛ぶが、ブランチ参照が古いまま残って追いにくくなる。

2. **作業ツリーがクリーンで、検証が通っていること。**

   ```
   ./gradlew check :shared:compileAndroidMain :androidApp:compileDebugKotlin :desktopApp:compileKotlin
   ```

3. **配布中の版を確認して、次の patch を決める。**
   `versionName` はタグ名そのものなので、番号は人が数える。

   ```
   gh release view latest --json name,tagName
   ```

## 打つ

```
git tag v0.1.13
git push origin v0.1.13
```

**タグの push は外部公開操作。実行の直前に必ずユーザーへ確認を取る。**
依頼済みであっても、押す瞬間に改めて一声かける。

## 確認する

```
gh run list --limit 3
```

`Release` ワークフローが走る（8 分ほど）。成功すると 2 つのリリースができている。

- **`v0.1.13`** … 版ごとの記録。配布物の実物が残るので、後からどの版で何を配ったか辿れる
- **`latest`** … 更新経路。配布済みのアプリはここからマニフェストと配布物を引く

手元の端末では、設定画面の「アプリの更新」から確認・適用できる。

## 気をつけること

- **タグの打ち直しは効かない。** `versionCode` はコミット数なので、同じコミットに打ち直しても
  値が変わらない。既に更新した端末には二度と降りない。直すときは patch を上げる。
- **版を下げる手段は無い。** Android は `versionCode` が下がるインストールを拒み、MSI も版数の
  増加を置き換えの条件にしている。戻すにはアンインストールが要り、設定と履歴が消える。
  問題が出たら戻すのではなく、直した版を出す。
- **接尾辞つきのタグは通らない**（`v1.0.0-rc1` 等）。MSI の版数が major.minor.patch に限られる
  ため、ワークフローが弾く。
- **`latest` の置き場は動かさない。** 配布済みのアプリは取得先を `latest` 固定で組み立てている
  （マニフェストが指す URL を信用しない設計）。ここを動かすと全端末が更新を見つけられなくなる。
- 公開の前に、配布中の `latest.json` より `versionCode` が増えていることをワークフローが確かめる。
  ここで落ちたら、履歴の取得漏れかタグの打ち間違いを疑う。

## 配布せずに実機で試したいとき

`Release` ワークフローを **workflow_dispatch で手動実行**すると、署名済みの APK が成果物として
残るだけで、リリースには一切触れない。`latest` が動かないので他の端末には何も降りない。

落として手元の端末にだけ入れて確かめられる。**成果物は 3 日で消えるので、その間に落とす。**
`versionName` は `dev-<短縮 SHA>` になる。
`versionCode` はタグを打つ場合と同じくコミット数なので、後から出す正式な版は必ずこれを上回り、
更新として降りてくる。

MSI は版数の形式が合わないため手動実行では組まない（Desktop は手元でビルドできる）。
